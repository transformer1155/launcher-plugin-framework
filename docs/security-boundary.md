# 安全边界声明

这份文档对应规格第 7 节。它不是"注意事项"，而是**这套架构的诚实边界**：
下面每一条都是"当前实现做不到"或"做不到保证"的地方，请按此评估风险。

## 1. 可信插件与宿主同等权限

可信插件（签名有效且未被吊销）直接运行在**宿主进程的同一执行上下文**中。这意味着：

| 威胁 | 是否拦得住 | 拦不住的原因 |
|---|---|---|
| Rust `panic!` / `unwrap()` 失败 | ✅ 拦得住 | `catch_unwind` 包住每次 `Future::poll` |
| `std::process::abort()` | ❌ 拦不住 | 进程立刻终止，unwind 表无用 |
| `std::process::exit(0)` | ❌ 拦不住 | 同上 |
| 段错误 / UB / 野指针 | ❌ 拦不住 | 是 OS 层信号，不是 Rust unwind |
| OOM（分配失败或耗尽内存） | ❌ 拦不住 | 共享 allocator，OS 直接杀进程 |
| `panic = "abort"` 编译的任何 panic | ❌ 拦不住 | abort 模式不生成 unwind 表 |
| `extern "C"` 边界的 panic | ❌ 拦不住 | Rust 里这是 UB，无法可靠捕获 |
| 读其他插件/宿主的内存 | ❌ 拦不住 | 同一地址空间，无进程边界 |
| 调用任意宿主内部函数 | ❌ 拦不住 | Rust 没有 API 白名单机制 |

**唯一的防线是签名校验。** 一旦一个恶意包通过了验签（例如官方私钥泄露），它就能做上述
任何事。因此私钥保管与吊销响应速度是这套架构的安全等级上限，而不是代码里的隔离措施。

**实践建议**：把"可信"级别只授予你自己团队编写的、经过 review 的插件。第三方插件
即使能拿到签名，也应考虑强制走沙箱（见 `docs/open-questions.md` Q1）。

## 2. 沙箱插件不是安全沙箱

"虚拟进程执行单元"是调度器内的一个**数据结构**：

```rust
Unit {
    handle: UnitHandle,          // plugin_id + generation
    config: UnitConfig,          // 配额参数
    state: AtomicU8,             // Running / Crashed / ...
    in_flight: AtomicU32,        // 并发计数
    slots: Mutex<HashMap<..>>,   // 在飞任务（用于 cancel / abort）
    rate: Mutex<RateWindow>,     // 调用速率窗口
}
```

执行 handler 的是宿主 tokio 线程池的 worker 线程。**没有** fork、子进程、WASM 实例、
独立地址空间。

它提供的隔离：

- **逻辑隔离**：状态、配额、超时、崩溃后重建，互不污染；
- **API 限制**：插件只能通过工具注册表暴露的函数调用其他插件（框架层面成立，
  但 Rust 无法在语言层阻止恶意代码直接调用宿主内部函数）；
- **资源配额**：并发数、调用速率、返回体积、生命周期（空闲/最长存活）。

它**不能**提供的隔离：

| 威胁 | 是否拦得住 | 说明 |
|---|---|---|
| 读宿主或其他插件内存 | ❌ | 同一地址空间 |
| 直接调用宿主内部 API | ❌ | Rust 无 API 白名单机制 |
| 耗尽内存 | ❌ | `memory_limit_bytes` 是**声明性字段**，无法强制执行 |
| 逃逸到 native | ❌ | 本身就是 native 代码 |
| 无限循环占满一个 worker | ⚠️ 部分 | 能被探针判定为"不可中断"并升级为单元崩溃，但**该线程在被判定之前一直被占用** |

### 关于 `memory_limit_bytes` 的诚实说明

`UnitConfig::memory_limit_bytes` 在纯 Rust 单元里**无法强制执行**：宿主线程与 handler
共享同一 allocator 与地址空间，没有 per-unit 的计量点。它当前的作用是：

1. 通过 `list_units()` 透出给 UI，让用户看到插件声明的内存预算；
2. 作为未来 WASM 沙箱实现的配置入口。

**要真正强制执行内存上限，唯一的路径是把沙箱执行单元实现为 WASM 字节码沙箱**
（自有线性内存 + 指令计量 + 无 native 逃逸）。在此之前，请不要把这个字段理解为
"内存被限制了"。

### 关于"不可中断"的实质

`std::thread::sleep` / 密集计算这类不产生 await 点的代码，`abort()` 是**无效**的：

- 我们能做的：通过探针判定它卡在 poll 内，把整个单元标记为 `Crashed` 并触发重启；
- 我们**不能**做的：抢占那个正被占用的 OS 线程。

因此一个恶意的、写死循环的沙箱插件仍然可以在被判定前的一段时间内吃满一个 worker。
缓解手段是保证 tokio worker 数 ≥ 2，并在 `uninterruptible_grace_ms` 之后立刻判定。

## 3. 重启管理器不覆盖可信插件

`RestartManager` 只订阅**沙箱单元**的崩溃事件（`Scheduler::on_crash`）。

- 可信插件不在调度器里 → 没有单元 → 没有崩溃事件 → 重启管理器看不到它；
- 可信插件的 panic 由 `catch_unwind` 捕获并返回 `HandlerPanic`，**宿主继续运行**，
  该工具**不会**被重启（它没有进程可重启，代码就在宿主里）；
- 可信插件若发生 abort/段错误/OOM → **宿主进程已死**，恢复只能靠用户重启启动器。

代码里的证据：`RestartManager::watch_plugin` 只被 `PluginLoader::load_sandboxed` 调用；
`load_trusted` 路径里不出现 `create_unit`，也不出现 `watch_plugin`。
测试 `restart_manager_only_manages_sandboxed_plugins` 断言了这一点。

## 4. "降级 vs 拒绝"的边界

规格说"签名校验失败时降级到沙箱，不拒绝加载"。但不是**所有**校验失败都该降级：

| 情况 | 处理 | 理由 |
|---|---|---|
| 无签名 | 降级到沙箱 | 规格明文要求 |
| 签名无效（摘要不符） | 降级到沙箱 | 规格明文要求 |
| 签名者被吊销 | 降级到沙箱 | 规格明文要求 |
| 算法不支持 | 降级到沙箱 | 等价于"无法验证" |
| 吊销列表自身验签失败 | **所有插件**降级到沙箱 | fail-closed：无法判断谁被吊销 |
| **运行期发现包摘要变化** | **标记 Failed，不重启** | 这不是"没签名"，是签名之后被改写；重启会执行被篡改的代码 |
| 清单缺失 / plugin_id 不一致 | 拒绝加载 | 不知道 plugin_id 就无法安全分派 |

最后两条是本实现相对规格的解���延伸，已在 `docs/open-questions.md` 里列出待确认。

## 5. 宿主构建配置的硬要求

1. **`panic = "unwind"`**（默认）。若宿主用 `abort`，可信插件机制不成立 ——
   请不要在那种模式下启用可信插件。
2. **tokio `multi_thread`，`worker_threads >= 2`**。单 worker 时，一个不可中断的
   handler 会占死唯一 worker，超时计时器与状态收敛全部停摆，"逻辑隔离"名存实亡。
3. **单进程**。不要为了"更安全"而给插件起子进程 —— 那违反本框架的进程模型前提
   （规格第 1 节），并且会引入 IPC 面，反而扩大攻击面。
