02架构设计Architecture

单进程插件模型：0 IPCSingle-Process Plugin Model: 0 IPC

传统插件启动器每调用一次插件就要 spawn 子进程或走管道往返：序列化、进程切换、句柄管理全是成本。Aether 让 Classic launcher architectures spawn a child process or do pipe round-trips per plugin call — serialization, context switches and handle juggling everywhere. Aether instead 插件与宿主共享同一 OS 进程shares one OS process between host and plugins ：插件工具就是一个 async 函数，注册进注册表后由调度器直接以 : a plugin tool is just an async function; once registered, the scheduler invokes it directly as a tokio 任务执行。参数用一次 JSON 跨界（MCP 语义要求），之后全程零拷贝引用。 tokio task. Parameters cross one JSON boundary (required by MCP semantics); everything after that is zero-copy references. 

┌─────────────────────────── one OS process ───────────────────────────┐
│  MCP Server (:3721) ──► Registry ──► Scheduler ──► handler()       │
│        ▲                                        │  timeout probe     │
│        │                                        ▼                    │
│   Claude / Cursor                        tokio::spawn(plugin task)  │
│                                                │  catch_unwind       │
│  GUI (Win32 FFI, immediate mode) ◄── state ────┘                     │
└──────────────────────────────────────────────────────────────────────┘
  • 无进程边界No process boundary — 调用即函数调用，返回即 Future 完成；没有管道粘包、没有协议协商。A call is a function call; a return is a completed Future. No pipe framing, no protocol negotiation.
  • 成本转移到信任层Cost shifted to the trust layer — 同进程意味着插件有能力做任何宿主能做的事，因此框架把安全性押在「签名信任 + 沙箱降级」上（见 §5）。Same-process means a plugin can do anything the host can, so safety is delegated to the signature-trust + sandbox-degradation model (see §5).
  • 崩溃不等于失联Crash ≠ lost contact — 沙箱插件的 panic 被 L1 捕获为结构化错误并按退避策略重启。A sandboxed plugin's panic is captured by L1 as a structured error and restarted with backoff.

L0–L4 框架分层Framework Layers

框架核心位于 src/，自下而上五层，依赖方向严格单向： The framework core lives in src/ in five bottom-up layers with a strictly one-way dependency direction: L4 → L2 → L1 → L0 ；L3 只被 L2 / 入口使用，L1 不认识 L3。 ; L3 is only consumed by L2 / the entry point, and L1 never knows about L3.

Layercrates / modules职责Responsibility
L0 基础Foundationerror types json错误码、元数据、schema 校验。无异步、无锁。Error codes, metadata, schema validation. No async, no locks.
L1 执行Executioncatch_unwind scheduler虚拟进程执行单元、超时、取消、配额、状态机。Virtual-process execution units, timeout, cancellation, quotas, state machine.
L2 编排Orchestrationregistry restart工具登记与 ACL、四步检查分流、退避重启与熔断。Tool registration & ACL, four-step check routing, backoff restart & circuit breaking.
L3 信任Trustsignature loader包整体验签、吊销列表、降级决策。Whole-package signature verification, revocation list, degradation decisions.
L4 对外Interfacemcp与 MCP 无状态语义对齐（无 initialize 握手）。Stateless MCP semantics alignment (no initialize handshake).

异步任务与超时计时器的隔离机制Async Task & Timeout Isolation

每个 ToolDef 声明自己的 timeout_ms。调度器把 handler 放进独立 tokio 任务执行，外层套超时预算、内层用 catch_unwind 兜住 panic —— 单个插件的失控只消耗它自己的预算，宿主主循环不受影响： Every ToolDef declares its own timeout_ms. The scheduler runs each handler in an isolated tokio task, wrapped in a timeout budget, with catch_unwind underneath to contain panics — a runaway plugin only burns its own budget and never touches the host loop:

rust
use std::panic::AssertUnwindSafe;
use std::time::Duration;
use tokio::time::timeout;

/// 在隔离单元中执行一个工具调用：
/// - panic 被 JoinError 捕获，不会带崩宿主；
/// - 超过 budget 的调用被强制打断，JoinHandle 随后 abort 回收；
/// - 宿主主循环与其它插件完全不受影响。
pub async fn run_isolated<F, Fut>(factory: F, budget: Duration) -> UnitOutcome
where
    F: FnOnce() -> Fut + Send + 'static,
    Fut: Future<Output = ToolResult> + Send,
{
    // AssertUnwindSafe：handler 是外部插件代码，框架不假设它 UnwindSafe。
    let task = tokio::spawn(AssertUnwindSafe(async move { factory().await }));

    match timeout(budget, task).await {
        // 正常完成
        Ok(Ok(result)) => UnitOutcome::Done(result),
        // 子任务 panic：JoinError 携带 panic payload，转成结构化业务错误
        Ok(Err(join_err)) if join_err.is_panic() => UnitOutcome::Panicked,
        // 取消 / 其他 Join 异常
        Ok(Err(_)) => UnitOutcome::Cancelled,
        // 超时：预算耗尽。tokio 的 timeout 已放弃等待，
        // 调度器随后对残留任务 abort()，杜绝僵尸任务堆积。
        Err(_elapsed) => UnitOutcome::TimedOut,
    }
}
WHY 为什么 panic 必须在任务边界拦？Rust 的 panic 是 per-thread unwind。tokio::spawn 的任务跑在调度器线程池里，panic 在任务内 unwind 到任务边界被 JoinError 接住——宿主的 Registry / GUI 线程完全无感。这就是「Trap/Panic 隔离」的全部原理：隔离点选在任务边界，而不是试图让 unsafe 代码「不 panic」。 Why trap panics at the task boundary? Rust panics unwind per-thread. A tokio::spawn task runs on the worker pool, so its panic unwinds to the task boundary and is captured as a JoinError — the host's Registry / GUI threads never notice. That is the whole idea of trap isolation: the isolation point is the task boundary, not wishful "non-panicking" unsafe code.

handler 与 ToolResultHandler & ToolResult

handler 是一个A handler is an async fn(ctx: PluginContext, args: YourArgs) -> Result<ToolResult, ToolError> 。PluginContext 注入运行时能力（插件私有数据目录、受白名单约束的 HTTP 端口、日志）；返回值 ToolResult 与 MCP 的 tools/call 响应体逐字段同构： . PluginContext injects runtime capabilities (plugin-private data dir, allowlisted HTTP port, logging); the returned ToolResult is field-for-field isomorphic to the MCP tools/call response body:

rust
/// MCP `tools/call` 的返回体：`{ content, structuredContent, isError }`
pub struct ToolResult {
    pub content: Vec<ContentBlock>,          // Text { text } | Json { json }
    pub structured_content: Option<Value>,   // 结构化负载（AI 友好）
    pub is_error: bool,                      // 业务失败也走 200，用 isError 表达
}

// 两个现成的构造出口：
result::success(json!({ "os": "windows", "arch": "x86_64" }))          // is_error = false
result::business(biz_codes::UPSTREAM_ERROR, "上游 403")                // is_error = true
NOTE 错误码是字符串枚举（biz_codes，snake_case，如 storage_error / upstream_error）。业务失败不 panic、不返回 Err —— Err 保留给「工具根本没法执行」（参数非法、能力缺失），业务语义失败一律用 business() 把控制权交回 AI。 Error codes are string enums (biz_codes, snake_case, e.g. storage_error / upstream_error). Business failures neither panic nor return Err — Err is reserved for "the tool cannot run at all" (bad args, missing capability); semantic failures go through business() to hand control back to the AI.

rust
//! com.example.sysinfo —— 最小可编译插件示例。
//! 一个工具：get_sysinfo（返回 OS / 架构 / 逻辑核数 / 数据目录可写性）。

use launcher_plugin_common::result::{self, biz_codes};
use launcher_plugin_common::tool_args;
use launcher_plugin_common::{PluginContext, ToolDef};
use launcher_plugin_framework::error::ToolError;
use launcher_plugin_framework::types::ToolResult;
use serde_json::json;

// ---- 1. 入参：tool_args! 在编译期生成 JSON Schema + Deserialize ----
tool_args! {
    /// get_sysinfo 的入参。
    pub struct SysInfoArgs {
        /// 可选：附带一次数据目录可写性探测。
        check_writable: o_bool() = "是否检查数据目录可写性",
    }
}

// ---- 2. handler：async fn，与宿主同进程执行 ----
pub async fn handle(ctx: PluginContext, args: SysInfoArgs) -> Result<ToolResult, ToolError> {
    let os = std::env::consts::OS.to_owned();
    let arch = std::env::consts::ARCH.to_owned();
    let cores = std::thread::available_parallelism()
        .map(|n| n.get())
        .unwrap_or(1);

    let mut writable = None;
    if args.check_writable.unwrap_or(false) {
        // PluginContext 提供按插件 id 隔离的私有数据目录。
        let probe = ctx.data_dir().join(".write-probe");
        writable = Some(match std::fs::write(&probe, b"ok") {
            Ok(()) => {
                let _ = std::fs::remove_file(&probe);
                true
            }
            // 探测失败是「业务语义失败」：交回错误码，而不是 panic
            Err(e) => {
                return Ok(result::business(
                    biz_codes::STORAGE_ERROR,
                    format!("数据目录不可写：{e}"),
                ))
            }
        });
    }

    // ---- 3. 返回：structuredContent 与 MCP 响应同构 ----
    Ok(result::success(json!({
        "os": os,
        "arch": arch,
        "logical_cores": cores,
        "data_dir_writable": writable,
    })))
}

// ---- 4. ToolDef：注册表据此构建 ToolMeta（input_schema 在此挂载） ----
pub fn def() -> ToolDef {
    launcher_plugin_common::tool_def! {
        name: "get_sysinfo",
        description: "获取运行环境系统信息（OS / 架构 / 逻辑核数 / 数据目录可写性）",
        destructive: false,
        timeout_ms: 5_000,
        args: SysInfoArgs,
        handler: crate::sysinfo::handle
    }
}

05安全边界Security Boundary

Aether 的安全模型是「信任驱动」而非「沙箱保证」：先验签决定信任级别，沙箱只负责故障隔离。以下三小节说清它保护什么、不保护什么。 Aether's model is trust-driven, not "sandbox-guaranteed": verification decides trust level first, and the sandbox only provides fault isolation. The three subsections below state exactly what is protected and what is not.

native 代码逃逸风险（诚实声明）Native Escape Risk (Honest Disclosure)

! 沙箱插件 ≠ 安全沙箱。Sandboxed ≠ a security sandbox.
Aether 的沙箱目标是可用性隔离（防 panic、超时、配额失控拖垮宿主），不是完整性 / 机密性边界。插件与宿主同进程运行，native 代码可以通过 unsafe / FFI、直接文件系统访问、子进程派生、网络原始 socket 等方式绕过框架施加的一切约束。运行来路不明的插件 = 把本机权限交给它的作者。请只安装你信任来源的插件，并阅读 docs/security-boundary.md。 Aether's sandbox targets availability isolation (panics, timeouts and quota runaways cannot take down the host), not an integrity / confidentiality boundary. Plugins share the host process; native code can escape every framework constraint via unsafe / FFI, direct filesystem access, subprocess spawning or raw sockets. Running a plugin from an unknown author equals handing it your machine. Only install plugins from sources you trust, and read docs/security-boundary.md.
  • 签名解决「作者是谁」Signatures answer "who wrote it" — ；沙箱解决「它失控时宿主还能活着」; the sandbox answers "will the host survive if it misbehaves" — 两者都不能回答「它是否恶意」。neither answers "is it malicious".
  • 纵深防御Defense in depth — 白名单网络 + 数据目录隔离 + 破坏性工具二次确认，抬高误操作成本，但不构成硬边界。Allowlisted networking + per-plugin data dirs + destructive-tool confirmation raise the cost of accidents, but are not hard boundaries.

关键设计取舍（先看这三条）Key Trade-offs (Read These Three First)

  1. 沙箱单元不是线程，也不是线程池条目。A sandbox unit is not a thread, nor a pool slot. 它是一份 UnitConfig + 一组原子计数器（状态、心跳、并发配额、调用速率窗口）+ 一个代数（generation，用于让旧单元的迟到回调失效）。执行 handler 的仍是宿主的同一套 tokio 线程池——这正是「单 OS 进程内逻辑隔离」的物理含义。 It is a UnitConfig + a set of atomic counters (state, heartbeat, concurrency quota, rate window) + a generation counter (to invalidate late callbacks from old units). Handlers still run on the host's own tokio pool — that is the physical meaning of "logical isolation within one OS process".
  2. 超时计时器与被测 handler 不在同一个 future 里。The timeout timer and the handler never share one future. handler 跑在独立 spawn 的 task 上，计时器在调用方 task 上 race，因此 handler 阻塞 poll 时计时器仍然能触发。这是能区分「可中断超时」和「不可中断超时」的前提。 The handler runs on an independently spawned task while the timer races on the caller's task, so the timer still fires even when the handler blocks inside poll. This is the precondition for distinguishing interruptible vs uninterruptible timeouts.
  3. 可中断性靠心跳判定，不靠「abort 之后它死没死」。Interruptibility is judged by the heartbeat, not by "did it die after abort". abort 只能在下一次 await 点生效，所以 heartbeat 在超时时刻是否前进，就是「可中断 / 不可中断」的判据。 abort only takes effect at the next await point, so whether heartbeat has advanced at timeout time is the criterion for interruptible vs not.

2. 沙箱插件不是安全沙箱The Sandboxed Unit Is Not a Security Sandbox

「虚拟进程执行单元」是调度器内的一个数据结构： The "virtual-process execution unit" is a data structure inside the scheduler:

rust
Unit {
    handle: UnitHandle,          // plugin_id + generation
    config: UnitConfig,          // 配额参数
    state: AtomicU8,             // Running / Crashed / ...
    in_flight: AtomicU32,        // 并发计数
    slots: Mutex<HashMap<..>>,   // 在飞任务（用于 cancel / abort）
    rate: Mutex<RateWindow>,     // 调用速率窗口
}

执行 handler 的是宿主 tokio 线程池的 worker 线程。没有 fork、子进程、WASM 实例、独立地址空间。 Handlers run on the host tokio pool's worker threads. No fork, no child process, no WASM instance, no separate address space.

它提供的隔离Isolation it does provide：

  • 逻辑隔离Logical isolation — 状态、配额、超时、崩溃后重建，互不污染；state, quotas, timeouts, crash-and-rebuild stay independent;
  • API 限制API restriction — 插件只能通过工具注册表暴露的函数调用其他插件（框架层面成立，但 Rust 无法在语言层阻止恶意代码直接调用宿主内部函数）；plugins reach other plugins only through registry-exposed functions (holds at the framework level, though Rust cannot stop malicious code calling host internals at the language level);
  • 资源配额Resource quotas — 并发数、调用速率、返回体积、生命周期（空闲 / 最长存活）。concurrency, call rate, response size, lifetime (idle / max-age).

它不能提供的隔离Isolation it cannot provide：

关于About memory_limit_bytes 的诚实说明— an honest note

UnitConfig::memory_limit_bytes 在纯 Rust 单元里无法强制执行：宿主线程与 handler 共享同一 allocator 与地址空间，没有 per-unit 的计量点。它当前的作用是： UnitConfig::memory_limit_bytes is unenforceable in a pure-Rust unit: host threads and handlers share the allocator and address space, and there is no per-unit metering point. Its current roles:

  1. 通过 list_units() 透出给 UI，让用户看到插件声明的内存预算；surfaced to the UI via list_units() so users can see the declared budget;
  2. 作为未来 WASM 沙箱实现的配置入口。as the config entry point for a future WASM sandbox implementation.
! 要真正强制执行内存上限，唯一的路径是把沙箱执行单元实现为 WASM 字节码沙箱The only path to enforcing memory limits is a WASM bytecode sandbox （自有线性内存 + 指令计量 + 无 native 逃逸）。在此之前，请不要把这个字段理解为「内存被限制了」。 (own linear memory + instruction metering + no native escape). Until then, do not read this field as "memory is limited".

关于「不可中断」的实质What "uninterruptible" really means

std::thread::sleep / 密集计算这类不产生 await 点的代码，abort() 是无效的： For code that never hits an await point (std::thread::sleep, busy computation), abort() is ineffective:

  • 我们能做的What we can do — 通过探针判定它卡在 poll 内，把整个单元标记为 Crashed 并触发重启；probes detect the stuck poll, mark the unit Crashed and trigger a restart;
  • 我们不能做的What we cannot do — 抢占那个正被占用的 OS 线程。preempt the pinned OS thread.

因此一个恶意的、写死循环的沙箱插件仍然可以在被判定前的一段时间内吃满一个 worker。缓解手段是保证 tokio worker 数 ≥ 2，并在 uninterruptible_grace_ms 之后立刻判定。 A malicious sandboxed plugin with a hard infinite loop can still saturate one worker for a while before judgment. Mitigation: keep tokio workers ≥ 2 and judge right after uninterruptible_grace_ms.

3. 重启管理器不覆盖可信插件The Restart Manager Never Covers Trusted Plugins

RestartManager 只订阅沙箱单元的崩溃事件（Scheduler::on_crash）： RestartManager only subscribes to crash events of sandbox units (Scheduler::on_crash):

  • 可信插件不在调度器里 → 没有单元 → 没有崩溃事件 → 重启管理器看不到它；trusted plugins are not in the scheduler → no unit → no crash events → invisible to the restart manager;
  • 可信插件的 panic 由 catch_unwind 捕获并返回 HandlerPanic，宿主继续运行，该工具不会被重启（它没有进程可重启，代码就在宿主里）；a trusted plugin's panic is captured by catch_unwind and returned as HandlerPanic; the host keeps running and the tool is not restarted (there is no process to restart — the code lives in the host);
  • 可信插件若发生 abort / 段错误 / OOM → 宿主进程已死，恢复只能靠用户重启启动器。if a trusted plugin aborts / segfaults / OOMs → the host process is dead; recovery means the user restarts the launcher.

代码里的证据：RestartManager::watch_plugin 只被 PluginLoader::load_sandboxed 调用；load_trusted 路径里不出现 create_unit，也不出现 watch_plugin。测试 restart_manager_only_manages_sandboxed_plugins 断言了这一点。 Evidence in code: RestartManager::watch_plugin is only called from PluginLoader::load_sandboxed; the load_trusted path contains neither create_unit nor watch_plugin. Test restart_manager_only_manages_sandboxed_plugins asserts this.

5. 宿主构建配置的硬要求Hard Build Requirements for the Host

  1. panic = "unwind"（默认）。若宿主用 abort，可信插件机制不成立 —— 请不要在那种模式下启用可信插件。(the default). With abort the trusted-plugin mechanism is void — never enable trusted plugins in that mode.
  2. tokio multi_thread，worker_threads >= 2。单 worker 时，一个不可中断的 handler 会占死唯一 worker，超时计时器与状态收敛全部停摆，「逻辑隔离」名存实亡。With a single worker, one uninterruptible handler pins the only worker; timers and state convergence all stall, and "logical isolation" exists in name only.
  3. 单进程Single process。不要为了「更安全」而给插件起子进程 —— 那违反本框架的进程模型前提（规格第 1 节），并且会引入 IPC 面，反而扩大攻击面。Do not spawn child processes for plugins "for safety" — it violates the framework's process-model premise (spec §1) and adds an IPC surface, widening the attack surface instead.

Q1. 「无吊销列表」的发行版该怎么处理？Shipping without a revocation list? 影响 · 安全等级 · 高impact · security · high

现状Status： Ed25519Verifier 默认 require_revocation_list = true。未装载吊销列表时所有插件都判 RevocationUnverifiable → 全部降级到沙箱（fail-closed）。 Ed25519Verifier defaults to require_revocation_list = true. Without a loaded list, every plugin is judged RevocationUnverifiable → degraded to sandbox (fail-closed).

问题Problem： 规格说「吊销列表随启动器更新」，但没写「如果启动器没带吊销列表怎么办」。如果发布流程存在「首次启动 / 离线环境 / 吊销库尚未下载」的窗口，默认 fail-closed 会让所有插件（包括官方签名的）在那一刻降级为沙箱。 The spec says the revocation list ships with launcher updates but never says what happens when the launcher has none. If the release flow has a "first launch / offline / list not yet downloaded" window, fail-closed degrades every plugin — including officially signed ones — during that window.

当前选择Current choice： 默认 fail-closed，同时提供 .without_required_revocation_list() 逃生门。三选一 —— (a) 保持 fail-closed，吊销列表必须随二进制打包（推荐，最安全）；(b) 允许「无列表 = 无人被吊销」（启动更快，但被吊销的插件在这个窗口里能拿到可信权限）；(c) 无列表时只信任「内嵌在二进制里的核心插件」，其余降级。 fail-closed by default, with a .without_required_revocation_list() escape hatch. Three options — (a) keep fail-closed, bundle the list with the binary (recommended, safest); (b) treat "no list = nobody revoked" (faster start, but revoked plugins get trusted privileges in that window); (c) trust only core plugins embedded in the binary, degrade the rest.

Q2. 「运行期包被篡改」该降级还是拒绝？Runtime tampering: degrade or reject? 影响 · 加载策略 · 中impact · loading · medium

现状Status： 重启时重新验签，若发现 package.digest() != loaded_digest（运行期间包文件被改写），标记 Failed 并停止自动重启，而不是降级到沙箱继续跑。 On restart, re-verification compares package.digest() != loaded_digest; if the package was rewritten at runtime, it is marked Failed and auto-restart stops instead of degrading into the sandbox.

理由Rationale： 这不是「没签名」，而是「签名之后内容被改」。降级会让篡改后的代码在受限环境里执行；停止则明确告诉用户「这个包不可信了」。但规格只说了「校验失败 → 降级」，这一条严格讲超出了规格。 This is not "unsigned" — content was modified after signing. Degradation would run tampered code in a restricted env; stopping clearly tells the user the package is untrustworthy. However the spec only says "verification failure → degrade", so this strictly exceeds the spec.

待定TBD接受「篡改 → Failed」，还是要求一律降级？Accept "tampered → Failed", or require unconditional degradation?

Q3. 热重载时信任级别变化怎么处理？Trust-level changes across hot reload? 影响 · 生命周期 · 中impact · lifecycle · medium

现状Status： PluginLoader::hot_reload 拒绝跨级别迁移（Sandboxed ↔ Trusted），返回明确错误，要求先卸载再加载；同级迁移正常支持。 PluginLoader::hot_reload rejects cross-level migration (Sandboxed ↔ Trusted) with an explicit error, requiring unload + reload; same-level migration works normally.

难点Difficulty： 升级需要原子地切换已在册工具的 trust_level、unit_handle（清空）与 handler 来源。中途若有在飞调用，会出现「半可信」状态。当前选择是保守拒绝：跨执行上下文迁移一旦做错，就是把不可信代码提权到宿主，风险远大于「让用户手动重载」。 Upgrading requires atomically switching registered tools' trust_level, unit_handle (cleared) and handler source; in-flight calls mid-switch create a "half-trusted" state. Current choice is conservative rejection: a botched cross-context migration promotes untrusted code into the host — far riskier than asking the user to reload manually.

待定TBD是否值得实现原子迁移？（若实现，建议「卸载 + 重载」，并在 UI 显示「插件需要重启以应用新的信任级别」。）Is atomic migration worth implementing? (If so: unload + reload, with a UI notice "plugin restart required to apply new trust level".)

Q4. cancel 遇到「任务已结束」该返回什么？— what should cancel of a finished task return? 影响 · 接口语义 · 低impact · API semantics · low

现状Status： CancelOutcome 有 5 个变体，规格只定义了 2 个（Cancelled / Uninterruptible），实现补了 AlreadyFinished / AlreadyTimedOut / NotFound —— 塞进 Cancelled 是在说谎，塞进 Uninterruptible 会误导调用方去重启插件。 CancelOutcome has 5 variants; the spec defines only 2 (Cancelled / Uninterruptible). The implementation adds AlreadyFinished / AlreadyTimedOut / NotFound — collapsing them into Cancelled would lie, into Uninterruptible would mislead callers into restarting the plugin.

协议视图Protocol view： as_protocol_str() 把前四个映射为 "Cancelled"，只有 Uninterruptible 映射为 "Uninterruptible" —— 对外的二元语义完全符合规格，多出来的变体只是内部精度。 as_protocol_str() maps the first four to "Cancelled" and only Uninterruptible to "Uninterruptible" — the external binary semantics fully matches the spec; extra variants are internal precision only.

Q5. 参数校验放在第几步？Which step does argument validation run at? 影响 · 用户体验 · 低impact · UX · low

现状Status： 检查顺序是 ①工具存在 → ②ACL → ③执行单元状态 → ④参数校验 → ⑤分流执行。规格的四步检查里没有参数校验。放在状态检查之后是因为：插件正在重启时返回 ProcessRestarting 比 InvalidArguments 更准确 —— 用户改参数也没用，得等插件起来。替代方案是放在 ACL 之后、状态之前（参数错误立刻反馈，但重启期间会误导用户去改参数）。 Order: ①tool exists → ②ACL → ③unit state → ④argument validation → ⑤dispatch. The spec's four-step check omits validation. Placing it after state-check because, while a plugin is restarting, ProcessRestarting is more accurate than InvalidArguments — changing args won't help until the plugin is back. Alternative: right after ACL (instant feedback on bad args, but misleading during restarts).

待定TBD保持现状，还是调整顺序？Keep as-is, or reorder?

Q6. list_tools 的's available 与调用结果的组合语义combination with call results 影响 · UI · 低impact · UI · low

现状Status： 重启期间 list_tools 返回 available: false, reason: "restarting"，而 call_tool 立即返回 ProcessRestarting。组合语义是「UI 灰掉按钮 + 若用户硬点则显示重启中」。available 是给 UI 的提示，不是准入开关 —— 真正的准入是 call_tool 里的状态检查。实现允许调用但立即失败（不排队），否则竞态窗口里「UI 显示可用但调用被拒」更令人困惑。 During restarts list_tools returns available: false, reason: "restarting" while call_tool immediately returns ProcessRestarting — i.e. "gray out the button; if the user insists, show 'restarting'". available is a UI hint, not an admission gate — real admission is the state check inside call_tool. The implementation allows the call but fails it immediately (no queueing); rejecting at the registry level instead would create the more confusing "UI says available but the call is rejected" race window.

Q7. 沙箱崩溃的错误码粒度Error-code granularity for sandbox crashes 影响 · 可观测性 · 低impact · observability · low

现状Status： handler panic → ProcessCrashed；超时可中断 → Timeout；超时不可中断 → Uninterruptible（同时升级为单元级崩溃）；重启失败 → ProcessFailed；重启中 → ProcessRestarting。规格的 ProcessCrashed 与 Uninterruptible 有语义重叠（后者也是崩溃），实现让 Uninterruptible 优先返回（更具体的原因），单元状态同时变为 Crashed。 handler panic → ProcessCrashed; interruptible timeout → Timeout; uninterruptible timeout → Uninterruptible (also escalated to unit crash); restart failure → ProcessFailed; restarting → ProcessRestarting. The spec's ProcessCrashed overlaps semantically with Uninterruptible (the latter is also a crash); the implementation returns Uninterruptible first (more specific cause) while the unit state becomes Crashed.

待定TBD若希望协议层统一表现为 ProcessCrashed（Uninterruptible 仅作内部原因），可以改。当前选择是「更具体的错误码优先」。If you prefer the protocol to always show ProcessCrashed (with Uninterruptible as internal cause only), that can change. Current choice: more specific code wins.

Q8. 是否要把沙箱换成真正的 WASM？Replace the sandbox with a real WASM sandbox? 影响 · 架构 · 大impact · architecture · major

现状Status： memory_limit_bytes 是声明性字段，无法强制执行（见 附录 B §2）。如果产品定位里「沙箱」要能真正限制内存与 CPU，纯 Rust 单元架构做不到，必须把执行单元换成 WASM 字节码沙箱（wasmtime / wasmer 之类）。 memory_limit_bytes is declarative and unenforceable (see Appendix B §2). If the product requires real memory/CPU limits, the pure-Rust unit cannot deliver; the unit must become a WASM bytecode sandbox (wasmtime / wasmer etc.).

这是架构级决策This is an architecture-level decision， 会改变：handler 的形态（从 Arc<dyn Fn> 变成 WASM 导出函数）、参数/返回值通道（从 serde_json::Value 变成 WASM 内存里的序列化数据）、启动开销（实例化 WASM 模块 vs 直接调用）。若答案是「否」，应当现在改架构，而不是后面补 —— 因为 handler 的类型签名会变。 It changes: handler shape (Arc<dyn Fn> → WASM exports), the argument/return channel (serde_json::Value → serialization into WASM memory), and startup cost (module instantiation vs direct call). If the answer is "we need real limits", change it now, not later — the handler type signature is involved.
